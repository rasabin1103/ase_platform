# Database

## Source of truth (local dev)

Schema migrations are managed with **Alembic** in `backend/alembic/versions/`. Migrations are hand-written (not autogenerated blindly) and each one is verified in both directions (`upgrade`/`downgrade`) with `--sql` before merging.

```powershell
cd backend
.venv\Scripts\alembic.exe upgrade head
```

Notable additions from recent work: `blog_posts` (public blog, admin-managed), `catalog_categories` + `catalog_items.custom_fields_json` (dynamic catalog categories with per-category custom field schemas). See `backend/app/models/blog_post.py` and `backend/app/models/catalog_category.py`.

## Scripts (`backend/scripts/database`)

| Script | Purpose |
|--------|---------|
| `reset_database.py` | Drop schema via Alembic downgrade + upgrade |
| `seed_roles.py` | MVP roles & permissions |
| `seed_users.py` | Demo users (super_admin, independent_user) |
| `seed_catalog.py` | Demo catalog items |
| `seed_all.py` | Roles → users → catalog |

Fresh setup:

```powershell
cd backend
.venv\Scripts\python.exe scripts\database\reset_database.py
.venv\Scripts\python.exe scripts\database\seed_all.py
```

Set `DEMO_SEED_PASSWORD` in `.env` before seeding (default in `.env.example`: `ChangeMeDemo123!`).

Two other seed scripts exist outside `scripts/database/`: `backend/scripts/seed_initial_data.py` and `backend/scripts/seed_demo_rbac.py` — the latter builds the full Organization → OrganizationMember → MemberRole → Role chain used by the RBAC demo accounts (see [rbac-architecture.md](rbac-architecture.md)).

## Test database

The backend pytest suite added in this round of work (`backend/tests/conftest.py`) needs its own disposable database via `TEST_DATABASE_URL` — it truncates every table before each test, so it must never point at the same database as `DATABASE_URL`. If `TEST_DATABASE_URL` isn't set, those tests skip cleanly rather than running against the wrong database. See [DEPLOYMENT.md](DEPLOYMENT.md#7-automated-tests) for the full picture, including an older, separate set of test files that predates this work and runs directly against whichever `DATABASE_URL` is active.

## Alembic is the only source of truth for the schema

An earlier `supabase/` folder with hand-written reference SQL (users, RBAC, catalog, favorites, purchases, access_requests) has been removed — it only ever covered a handful of MVP-era tables, was never kept in sync with the ~45 modules the app has grown into since, and pointed at a `ase_backend/` path that doesn't exist in this repo. Alembic (`backend/alembic/versions/`) is now, as it already effectively was, the single place that defines and applies the schema, on any Postgres provider (Supabase, RDS, Neon, self-hosted). Always run `alembic upgrade head`; there is no alternative SQL path to keep in sync anymore.
